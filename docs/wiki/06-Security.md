# 6. Security

MoonlightWeb exposes a streaming server to the LAN and, optionally, to the public Internet. The security model is layered: transport security (TLS), authentication (PIN / certificate file / host key), session management, abuse mitigation, and legal traceability.

## 6.1 Threat model in one paragraph

An instance opened to the Internet publishes no name, takes no certificate in its own name and opens no web port; what it exposes is a **held outbound line** and the router ports it maps for its tunnel and its stream slots. So there is no address to scan and no hostname in Certificate Transparency: a stranger's way in is to arrive at a known entry identifier and then get past the PIN. Attackers can: guess an identifier (128 bits, quota-bounded — [Infrastructure §10.12](10-Infrastructure-Stack.md#1012-hardening--limits)), scan/guess the PIN, flood connections, or replay stolen artifacts. Trusted parties: the local machine (localhost is admin, except under `--noadmin`), LAN clients (exempt from bans, still need a PIN when remote-auth applies). The introduction server is **partially** trusted — it knows which identifiers are online and sees residential addresses on its sockets, and it is deliberately kept out of the signalling's meaning by [§6.6](#66-the-entry-identifier-and-mw-bind-v1). Out of scope: volumetric DDoS, a compromised host OS.

## 6.2 Authentication

Three ways to obtain a session, all implemented in `AuthManager` + `AuthRoutes`:

| Method | Flow | Properties |
|---|---|---|
| **PIN** | Admin generates a 6-digit PIN on the admin page → remote user enters it once (`POST /api/auth/validate`) | Single-use in practice: a consumed PIN **auto-regenerates** and the admin UI shows `------` until a new one is explicitly generated. Rate-limited per IP. |
| **Certificate file** | Admin downloads a token file (`/api/admin/certificate/download`, 64+ random bytes Base64) → remote user uploads it instead of typing a PIN | Optional (`cert_auth_enabled`), revocable by regeneration. Compared in constant time. |
| **Host key** (`#k=`) | When the rendezvous line is up, the host machine's own entry points that are resolved at the click — the tray, the startup open, the installer's last page — open this machine's entry link with a long random key in its **fragment**, which the introduction server never receives. Redeeming it (`POST /api/auth/host-key`) proves the browser runs *on the host* although it arrives through the tunnel, not from loopback. Otherwise, and for the Desktop shortcut (a file written ahead of any click), they open `https://localhost`, where the address itself is the proof | Grants a **host session** (localhost-equivalent, admin-capable). **Single-use**: each redemption rotates the key, so a leaked link cannot be replayed. A local address may still carry it as `?mwk=`. |

A session can never revoke itself *as an administrator*: the admin page leaves the caller's own row out of the sessions table, and `POST /api/auth/sessions/revoke` answers 409 `cannot_revoke_self` regardless of what the UI does. Signing this browser out is not an administration task, and on the host machine's own session it would cost the admin access being used to click, plus the stream that session is flagged with.

Signing *yourself* out is a different route, and deliberately ungated: `POST /api/auth/logout` destroys the session the caller's own cookie belongs to and expires the cookie. It takes the raw cookie token, never an opaque id, so a browser can only ever reach its own session — the worst a visitor can do with it is lock themselves out. The admin-only path could not cover this case at all: someone who signed in from an internet café cannot open the host's admin page to get out, and without a way out they would walk away leaving a live session on a public machine. The Log out button sits at the bottom of the settings page, behind two conditions in `/api/auth/status`: the browser must hold a session (`has_session` — the host's own loopback page is authenticated by its address and has nothing to end) **and** must not be the host machine's own browser (`is_host_machine`, true for the loopback origin *and* for a host-key session reached through the public domain). The second condition is the one that is easy to miss: the host reaching its own server under the domain does carry a real session, but signing it out protects nothing — the credential is the machine itself — while costing the admin access being used to click, and dropping the owner onto a PIN prompt on their own PC. A LAN device that unlocked admin with the password is *not* the host and keeps the button: it is somebody else's computer, which is exactly the case the button exists for.

Losing the host session (expired, cookies cleared, revoked from another device) leaves the host machine's browser on the entry link looking like any other visitor — a PIN prompt, on the very machine that owns the server. Nothing in the request can safely say otherwise, so the way back is the one address that proves where the browser runs, `https://localhost` (the Desktop shortcut, or the tray when the line is down), which loads with local privilege and stays there; or a fresh link from the tray, which carries a new key. A page opened on the machine's LAN address offers the `https://localhost` link on its login screen; under the entry link it cannot, since the public port may differ from the local one.

Requests from the machine itself bypass authentication entirely and are, besides host sessions and the remote admin password below, the only way to use `/api/admin/*`. Being local is never decided by the peer address alone, so a visitor the tunnel relays from loopback is not taken for the machine itself. The host machine reaching itself through its entry link proves it with the host key instead (`#k=`, above), which its own entry points carry.

### 6.2.1 Remote admin password (LAN, internet on request)

Admin access is otherwise granted by *address*: the host machine has it, nobody else ever does. That leaves the operator stuck when the host is a headless box, a machine they are not sitting at, or simply a PC in another room. The remote admin password is the second door.

Three states, in `AppSettings`: **unset** (remote admin on, no digest stored — the door is advertised but opens for nobody), **set** (a digest stored), **disabled** (`remote_admin_enabled: false`, nothing is accepted).

- **There is no built-in default password.** A documented default is public knowledge, and while the unlock only ever *promotes an already-authenticated LAN session*, that still means "whoever can stream can also administer" on every install whose owner never changed it. So the door ships shut and `validateAdminPassword` matches nothing until a password exists. Setting one takes the host, which is exactly what the two entry points cover:
  - **with a desktop**, from the admin page, which the owner can always open locally;
  - **headless**, from the terminal — `moonlightweb --set-admin-password`, which the installer prompts for during a headless install, and which `--status` reports as unset until then.
- **Changed from the admin page or the CLI** (`POST /api/admin/password`, admin-gated). Stored as **PBKDF2-SHA256, 210 000 iterations, 16-byte random salt** — the plaintext is never written, so a forgotten password is *reset*, never recovered. Minimum 8 characters (400 `too_short`). **Removed** the same two ways (the admin page's *Remove password*, `moonlightweb --clear-admin-password`, both `{clear: true}`): back to *unset*, every unlock revoked.
- **Spent by an already-authenticated LAN device** (`POST /api/auth/admin-unlock`). It **promotes an existing session** rather than creating one: a device still has to pass the PIN first. The password raises what an admitted device may do; it never admits anyone.
- On a socket, two independent gates keep it off the Internet, because either one alone is forgeable in a deployment we support:
  - the peer address must be LAN (`AuthManager::isLanAddress` — loopback, RFC 1918, link-local, `fc00::/7`), **and**
  - the `Host` header must name this machine (`RequestGuard::isTrustedHost`). A TLS-terminating tunnel makes every visitor look like `127.0.0.1`, which the peer check alone would accept; a hairpin-NAT LAN client arrives under the public domain, which the Host check alone would accept for Internet visitors too. Both together admit exactly the LAN.
- **From the internet, only when the owner asks for it** (`remote_admin_internet`, off by default — a second checkbox under the LAN one). A peer outside the LAN may then spend the password **through the rendezvous tunnel only**: it already holds a session it earned with the PIN over that link, the address it is judged by is the one ICE settled on, and the password comes on top. A direct connection from a public address stays refused, since a proxy on this machine is exactly what forwards the whole internet here. Closing the internet side revokes every unlock, like a password change: which ones it bought is not recorded.
- Failed attempts use **their own rate-limit bucket** (`admin|<ip>`), on the same 3/5/10 → 30 s/2 min/10 min tiers, so hammering the password cannot lock a legitimate user out of PIN login (or vice versa). An attempt from outside the LAN also feeds **one bucket shared by the whole internet** (`admin|internet`, same tiers): an address costs nothing to change there, and the LAN never feeds it.
- An unlock belongs to the session, not to the place it is used from: a session unlocked on the LAN stays admin when the same browser later arrives from the internet.
- **Changing the password, or disabling remote administration, revokes every unlock the old one bought** (`demoteAdminSessions`) — except the caller's own when they are the remote admin doing the reset. Sessions survive; only the admin flag is dropped. Disabling and re-enabling restores the operator's password: the digest is kept. A persisted `is_admin` is discarded at load whenever the door is shut — remote administration off, or no password set.
- An unlocked LAN admin gets `isLocal` (full admin), but **not** `isHostMachine`: it never receives the host key and never sees the first-run setup wizard, both of which belong to the machine with the local desktop.

### 6.2.2 Booth mode (`--noadmin`)

A pre-configured machine left to visitors: they stream the hosts already set up and change nothing. Asked for in issue #26; the point is a "launch and done" screen, not a defence against whoever sits at the machine.

- **Nobody administers.** `RequestGuard::Context::adminLocked` makes `adminPrivilege` false for every caller — the host machine, an unlocked LAN session, the operator CLI — so every "localhost only" route answers 403 and `/api/admin/token` hands out no key. The admin password is not accepted either: `/api/auth/admin-unlock` is refused.
- **The host list is frozen.** Host routes were never admin routes (any session may add, pair or remove a host), so `RequestGuard::lockedByNoAdmin` refuses them outright with `403 admin_locked`: scan, manual add, remove, rename, pair, restart a host's service, set up its backend, its seats. Under `/api/hosts/:id/` it is an allow-list — `wol`, `start`, `quit`, `stop-session` — so a route added later is locked until it says otherwise. The self-update and `/api/system/*` are refused the same way.
- **No new device, no new guest.** PIN login (`/api/auth/validate`), share slots and a guest's PIN are refused. Devices paired before keep their sessions. A browser with none is shown "Booth mode" instead of the PIN page. One exception, off by default: see the next point.
- **Sharing from a booth** (issue #40). In `settings.json` ([where it lives](07-Settings-Reference.md#71-settingsjson-location)), set `"share_in_booth_mode": true`, then restart MoonlightWeb. **Share** comes back during a stream, and the share slots and a guest's PIN are let through again; nothing else is: no PIN login for a new device, no admin, the host list stays frozen. **What it gives away**: a share link is made to travel, and a guest invited at the **Desktop** or **Full** level drives the host's keyboard and mouse like whoever streams from the booth, so they can do on the host PC whatever the booth's visitor can, and more, since they are not sitting in front of the booth. The booth's own limit still applies: nothing stops a guest from restarting MoonlightWeb without the flag if the host session has the rights to. Set the key back to `false` (or remove it) and restart to close it again.
- **The host machine still streams.** `/api/auth/status` reports `admin_locked` and keeps `authenticated` for `isHostMachine` with no PIN; `is_localhost` (admin) is false. The front hides what it can no longer use: admin button and page, setup wizard, "Add manually", the host menu but Stop session, Pair, the update banner, Share (unless `share_in_booth_mode`). The tray keeps Open and Streaming only.
- **Getting admin back** is restarting without the flag. The limit is stated plainly: anyone with enough rights on the machine can do that too — run it as the service or under another account, visitors on a standard account. The installer and an update rewrite the logon task with `--autostart` alone, so the flag has to be added back after one.

## 6.3 Sessions

- A successful auth issues a random token in the `mw_session` cookie. **Only its SHA-256 (base64url) is stored** — in memory and in `sessions.json` — so a stolen sessions file cannot be replayed.
- **Sliding expiration**: 90 days of inactivity (`SESSION_TTL_SECS`); any authenticated request bumps `lastSeen`. Expired sessions are purged periodically; persisted sessions already expired by inactivity are discarded on load.
- **"Remember me" declined** (`remember: false` on `/api/auth/validate`, the checkbox on the login page, on by default): the session is marked `ephemeral` and differs in three ways. Its cookie carries **no `Max-Age`**, so it dies with the browser process; its inactivity budget is **8 hours** (`EPHEMERAL_SESSION_TTL_SECS`) instead of 90 days; and it is **never written to `sessions.json`**, so a restart ends it too. The cookie refresh in `/api/auth/status` re-checks the flag — adding a `Max-Age` there would silently promote a temporary login to 90 days. A session cookie alone would not be enough: the browser on a public machine is rarely closed, and the short server-side TTL is what actually ends an abandoned session there.
- Sessions carry IP, machine name (renameable), geolocation (async `GeoIpService` lookup, refreshed when the IP changes), a `streaming` flag (single active stream), `is_host`, and `is_admin` (unlocked with the remote admin password — see §6.2.1).
- **Revocation is immediate**: destroying a session that is actively streaming emits `streamingSessionRevoked`, which tears the live relay down and cancels the browser's Sunshine session (kill-switch in `main.cpp`).
- `POST /api/auth/regenerate` (a new PIN that revokes) invalidates **all** sessions; a new PIN from the admin page or `--new-pin` leaves them alone.
- HMAC signing key: generated once, persisted (`hmac_key` in settings) so sessions survive restarts.

## 6.4 Brute-force & flood mitigation

Two cooperating layers:

1. **`AuthManager` secret rate limiting** — per rate-limit bucket (raw IPv4, or /64 prefix for IPv6 — a client trivially owns a whole /64): 3 failures → escalating lockouts (30 s → 2 min → 10 min), remaining attempts surfaced to the UI. Constant-time comparisons throughout. The PIN and the remote admin password each get their own bucket per address.
2. **`ConnectionGuard`** — in-process fail2ban equivalent (fail2ban itself is Linux-only), checked at `accept()` time so banned IPs cost no TLS handshake:
   - Connection flood: > 200 new TCP connections / 10 s / IP (generous because a client that asks for `Connection: close` gets a socket per response — one page load can burst dozens of connections).
   - Auth-failure flood: > 10 rejected (401) requests / 60 s / IP.
   - Both arm a **10-minute temporary ban**; entries idle 5 min are purged.
   - **Loopback and private addresses (RFC 1918 / ULA / link-local) are fully exempt** — LAN clients are trusted.

## 6.4b Session sharing (invited players)

A share link is *designed* to leave the machine — it travels over chat apps, gets screenshotted, ends up in someone's history. So it is never a credential on its own.

- **Two factors, both ephemeral, both bound to one activation.** Opening a player row on the sharing board mints a 256-bit link token *and* a 6-digit PIN, and revokes whatever the previous opening produced. Token, PIN and the cookie the PIN buys are stored as SHA-256 digests and compared in constant time (`ShareManager`), like `mw_session`.
- **One device per invitation** (`kMaxCookiesPerActivation = 1`). The first device to spend the PIN is bound to that activation; the same correct PIN offered from a second one is answered `409 already_bound` and **does not touch the failure counter** — otherwise ten legitimate attempts would destroy the invitation the real guest is using. The refusal is recorded on the activation (time + User-Agent) and shown on the board, which is the point: forwarding the link *and* the PIN used to buy a silent second seat. This is the interim guarantee until a guest's key is bound to their device (`docs/design/pairing-signature.md` §"Not covered", phase 2) — a cookie cap, not a cryptographic proof.
- **The clear pair lives in memory only.** So the owner can reopen the row and read the link and PIN they already sent, `ShareManager` keeps them in the activation — but `share.json` receives digests and nothing else (`test_clear_secrets_are_memory_only`). A stolen data directory therefore yields no usable invitation, and a restart forgets the pair while the invitation itself stays valid: `POST /api/share/slots/:n/credentials` then answers `{available:false}` and the board says to regenerate. This is also why an *unlimited* invitation is honest rather than convenient: nothing in it is ever written to disk in the clear.
- **The PIN is asked for first.** `/api/share/player/info` reveals nothing — not even the machine name — until the device holds the `mw_player` cookie. A wrong PIN, an unknown token and an expired one produce the same answer. Link *liveness* is deliberately not hidden (whoever holds a 256-bit token already knows it existed; hiding it would make every expired link look like a typo).
- **Brute force costs the attacker the invitation.** Per-caller attempts follow the same tiered lockout as the PIN login on their own bucket, and **10 wrong PINs on one activation destroy it** — the owner sees the row go back to off and re-shares. Failures also feed `ConnectionGuard`, so a leaked link being hammered ends in the same 10-minute ban as credential scanning.
- **`mw_player` is not a session.** It never satisfies `isAuthenticated()`; it opens `/api/share/player/*` and the WebSocket upgrade of *its own* slot (`/ws2`…`/ws4`) and nothing else. Those slots reject the session cookie and the local-peer exemption alike — the player cookie is the only key.
- **The link names the player, the cookie only vouches for it.** `/info` and `/join` resolve the slot from the token in the URL and then require the cookie to resolve to that same slot; a mismatch is a PIN prompt, not an identity. Reading the slot off the cookie alone would let a browser holding player 1's cookie be answered as player 1 when it opens player 2's link.
- **Permissions are enforced in the worker.** The policy chosen on the board travels in the worker's launch config and filters every input message in all three transports plus the WS fallback (`InputMsg::allowed`); refused messages are dropped silently. The guest's page can send whatever JSON it likes. `ClipboardBridge` is off for any restricted session whatever the host address. The access level is a table over **both** flags — keyboard/mouse without a gamepad is `desktop`, not `full`, which is what the owner is actually granting.
- **The policy follows the board, live.** It is no longer frozen: `setPermissions` emits `permissionsChanged`, the supervisor sends `{"cmd":"setPolicy"}` down the worker's stdin, and the session swaps it on the relay thread that reads it. A demotion also calls `releaseHeldInputs(true)` — otherwise a key held at the moment its permission was revoked would stay down on the host forever, since the guest can no longer send the key-up and the owner never pressed it. The client's next heartbeat re-presses whatever it still holds *and* is still allowed to hold (`filterHeldState` runs against the new policy). The owner's own sessions carry no policy at all and stay unrestricted; `slotParam()` refuses the owner slots, so no share route can reach them.
- **Per-invitation lease, owner-controlled end.** Each row picks its own lifetime from a server-side whitelist — 1 h, 4 h, 8 h, 24 h, 48 h, or unlimited (`isValidTtl`; anything else is a 400, since the value arrives from a browser). Only an owner action (Close on the row, Stop, ⋯ → Stop session) or the lease ends an invitation; a dropped stream, a closed tab or a quality switch never do. The lease is checked at join *and* swept every minute so a live stream is cut at the deadline; an unlimited one is skipped by the sweep by construction.
- **The introduction server never sees the token.** A guest is reached through the rendezvous like everybody else, so the link is `https://stream.{domain}/{id}#t={token}`. The path names the machine — that server has to know which one to route the call to — and the invitation is in the **fragment**, which a browser never sends to the server it fetched the page from. It therefore appears in no request line, no query and no referrer, at any step: the bootstrap carries it across the handover into `/p#{id}&t={token}`, so it never occupies a URL path even after the application has started. The one form that does put it in a path is the LAN fallback, which is a direct TLS connection to the machine itself with nobody in between. Without a rendezvous the link is that LAN address and the board says so (`local_only`), rather than handing out an address that cannot open.
- **A guest reached this way is no longer relayed unsigned.** `docs/design/pairing-signature.md` listed a guest's signalling as a phase-2 blocker on the grounds that they hold no pairing key. Through the rendezvous their signalling travels *inside* the tunnel, and the tunnel itself is bound by MW-BIND-v1 with a key held per host identifier (`bootstrap/v1/pairing.js`, trust-on-first-use), so the relay is out of the middle for everything that follows. What that binding proves is the absence of a substituted peer, not who is holding the browser — authorisation is still the token and the PIN. Binding a guest's *credential* to their device remains unbuilt; the one-device cap above is what stands in for it.
- **Build-time switch**: `ShareManager::kSessionSharingEnabled = false` unregisters every route, so the whole surface answers 404 — indistinguishable from a build without the feature.

## 6.4c Invited players and administrator windows

On a **Windows** MoonlightWeb host, the windows that run as administrator are closed to invited players by default: an elevated console or PowerShell, Task Manager, an installer, a game started as administrator. Your own sessions are never held back.

- **What the guest sees.** While such a window has the host's focus, their keys and clicks on it are dropped. An orange strip says so: *An administrator window has focus on the host… click another window to continue.* Clicking any other window lets them carry on. This is MoonlightWeb's own rule (`policy` in the worker log). It is not the case where Windows itself refuses remote input (`uipi`, a MoonlightWeb that does not run elevated): that one blocks every viewer, you included, and its strip says so.
- **Why closed.** A share link is made to travel, and an administrator window is the whole PC: whoever drives an elevated console can install, delete or read anything on it. Handing that over is your decision, never a default.
- **What else counts as one.** A window MoonlightWeb cannot identify is held back like an administrator's: the secure desktop of a UAC prompt, which a stream worker that does not follow it sees as no window at all, or a window of a SYSTEM process. A guest's clicks, wheel and keys always go through `SendInput`, never through the virtual mouse and keyboard a host without them gets: a device's input reaches the secure desktop, `SendInput` does not. And a guest's **Ctrl+Alt+Del** is not sent: it opens the secure desktop, from which the host can be locked or its user signed out.
- **The moment of the press.** The window is checked as each press goes to Windows, which applies it after what came just before. So a guest's click or wheel goes in together with the position that was checked, and a guest's press right after something that switches windows (Alt+Tab, the Windows key, Ctrl+Shift+Esc, a click) waits up to a tenth of a second for the switch to finish. A few rare cases of timing and of relative pointer movement are not covered: treat it as a safeguard, not a wall.
- **The way out button.** The strip carries **Minimise the host's windows**, and an invited player with keyboard or mouse can press it. The host then minimises every window, the administrator one included, and puts back the others it can. It does so even when that window is your game, in the middle of a match. The button is there because a game run as administrator that fills the screen leaves a guest nothing else to click.
- **Opening them.** In `settings.json` ([where it lives](07-Settings-Reference.md#71-settingsjson-location)), set `"share_guests_admin_windows": true`, then restart MoonlightWeb. Every guest whose invitation gives keyboard and mouse (the **Desktop** and **Full** levels) is then let into administrator windows like you, and never sees the strip. A gamepad was never held back. The worker log of such a guest says `administrator windows open to this invited player (share_guests_admin_windows)`.
- **What it gives away.** Anyone holding the share link and its PIN, with keyboard or mouse ticked, can act as administrator on this PC, including on UAC prompts. The installed service's stream worker reaches the secure desktop, so the guest can also answer **Yes** to an elevation prompt and type on the lock screen (a PIN they would have to know). On a host with no keyboard, the virtual keyboard they then type through in gaming mode serves the normal desktop only: the secure desktop stays `SendInput`, which only the service's worker can reach. There are no levels in between: a guest who can drive an administrator console already is an administrator of the machine, so a halfway setting would protect nothing.
- **Closing them again.** Set the key back to `false` (or remove it) and restart MoonlightWeb.

## 6.5 TLS

- **LAN**: a self-signed certificate is generated on first run (browser shows a one-time warning — inherent to self-signed TLS).
- **From the Internet**: there is no certificate for this machine, and that is the design rather than a gap. A remote browser never opens a TLS socket to it: the page comes from the entry host under that host's own certificate, and everything after it travels inside the tunnel's **DTLS**, whose peer is verified against a key the browser pinned to this machine's identifier (§6.6). No certificate is issued, so no hostname of a user's machine ever lands in **Certificate Transparency** — which a publicly trusted certificate would have made permanent, public information.
- **Bring your own**: set `domain` to your FQDN and point `cert_pem`/`cert_key` at your PEM files (or drop them in the data dir's `cert/` folder). A certificate is accepted when it covers the domain by **CN or SAN**, wildcards included; renewal and lifecycle are the user's, and a certificate close to expiry is kept, never downgraded to self-signed. Full procedure, with the DNS/router side: [Settings Reference §7.5](07-Settings-Reference.md#75-bring-your-own-domain--certificate).
- Qt's TLS backend is forced to **OpenSSL** (Windows Schannel cannot import PEM keys — a user-supplied certificate would silently be dropped in favour of the self-signed one).
- `CertManager` guards the ordering traps that produced silent downgrades in the past: `loadCertFiles` precedence, a self-signed key colliding with a supplied one, and hot reload without dropping live connections.

## 6.6 The entry identifier and MW-BIND-v1

Being reachable and being trusted are two different things here, and the split is the point.

**The identifier is a locator.** `rendezvous_id` — 26 Crockford base32 characters, 128 bits — says *which machine*, and nothing more. Anyone may hold one; holding it lets nobody in. It is long so the set cannot be walked, and it never rotates so it can be bookmarked. What grants access is still the PIN, the certificate file or an invitation ([§6.2](#62-authentication), [§6.4b](#64b-session-sharing-invited-players)).

**Ownership of an identifier** is claimed once against the introduction server, which stores only `HMAC(rendezvous_token)` keyed by the identifier and requires the matching token on every later use (trust-on-first-use, per-IP quota on new claims). The token is a separate value from anything else the instance holds, deliberately: one credential authorising two unrelated things is one credential that cannot be retired independently.

**The introduction server is out of the middle, by construction.** It relays the DTLS fingerprints the two peers use to find each other — so a compromised one could substitute its own and sit between them. **MW-BIND-v1** is what stops that: the fingerprint is signed with the pairing key, which that server never sees, and the payloads it copies are opaque to it (`docs/design/pairing-signature.md`, `bootstrap/v1/pairing.js`).

Be precise about what the binding proves: **the absence of a substituted peer**, not who is holding the browser. It is trust-on-first-use, keyed per host identifier in the browser's own storage, so the first connection to a machine is the one that establishes what "this machine" means. Authorisation is a separate question, and it is answered by the PIN.

A browser arriving at the login screen holds no session, so the host cannot look its key up. It **presents** the key and the host signs against the key it was shown — enough to prove the channel was not substituted, and no claim at all about identity. See [Backend §3.4](03-Backend.md#34-internet-access-and-the-way-in).

## 6.6b One address for every machine

Every machine reached through the introduction server opens under the same address, `https://stream.{domain}/<id>`. That is by choice: one name users see and stream on, no name per machine, nothing per machine in DNS or in Certificate Transparency.

Since v0.4.1:

- **A session works only with the key it was paired on.** A cookie presented over a tunnel whose browser key is not the one its session was bound to is refused (401). The key cannot leave the browser it was made in, so a copied cookie is worthless anywhere else.
- **The cached interface is checked against its own machine on every start.** The machine's file list carries the SHA-256 of each file, sent over the channel its key signed. The entry page, served fresh by the introduction server, compares the cache with it before every start and fetches the interface again at the first difference. The service worker hands the cached interface only to a start the entry page has just checked.
- **No page connects to another machine any more.** The home-screen shortcut signs in on the machine it was made from; another machine asks its PIN the first time the shortcut opens it.

## 6.7 Internet-access consent & audit

Enabling Internet Access is an **explicit opt-in**, and nowhere is either answer pre-selected. A silent install (`/SILENT`, `/VERYSILENT`) shows no page and so leaves Internet Access off; `/INTERNET=yes` on its command line is the explicit answer, recorded with the text of the page and the fact that it came from the command line. A silent update keeps whatever the machine had. The installer asks with two buttons — **Passer** / **Accepter**, in that order, the affirmative one on the right — and the page cannot be walked past without pressing one; the setup wizard does the same with a two-button choice that holds its *Start* button until it is answered. Only the admin page keeps a checkbox, because there it is a state switch rather than a question. The consent is the mechanism that actually opens things: it gates the rendezvous line and the media mapping of the next streams; withdrawing it stops the line at once, while the router ports already mapped stay until MoonlightWeb exits. The exact agreement text, timestamp (ISO-8601 UTC), entry point (`admin` | `setup` | `installer`) and **mechanism version** are persisted (`internet_consent` in settings) — the record keeps *what the user was actually shown*, not a reference to a document that can be edited afterwards.

A consent only covers the mechanism its wording described. When the wording changes materially, a stored record from before it no longer authorises anything: the manager parks in phase `consent_required` and opens nothing until the user agrees again under the current text. That check is why the switch being left "on" across an upgrade is not, on its own, permission.

## 6.8 Other hardening

- `/api/admin/*` → 403 unless localhost, a host session or a session unlocked with the admin password (nobody under `--noadmin`); the internet/setup/system/local routes re-check the same `req.isLocal` predicate inside their handlers.
- Input to Sunshine is encrypted (AES-128-GCM, per-session key) as per GameStream.
- On a stream, private LAN ICE candidates are advertised **only to clients detected as local**. The control tunnel a remote browser arrives on always emits them: its peer's address is not known yet, and withholding them would cost a browser on the same network its direct path. A peer holding this machine's 128-bit identifier can therefore learn its private address, which says nothing about how to reach it.
- Per-browser `client_uniqueid` values are sanitized to hex (max 32 chars) before reaching launch URLs.
- Session cookies are the only client-held secret; settings/keys/certs are server-side only.
- Frontend escapes all interpolated HTML (`escapeHtml.js`).
- A request that arrives through the tunnel **never** obtains the local-address exemption, enforced in `HttpServer::serveRequest()` rather than at the call site.
- CI embeds the `MW_*` service credentials into the binary at build time — installers ship **no editable secrets** on disk; runtime env/.env still override.
- **Distribution integrity**: Windows binaries and the installer are Authenticode-signed via SignPath; the APT repository is trusted through a signed `InRelease`, the DNF one through both a signed `repomd.xml` and per-package `rpmsign` signatures; the Homebrew cask and AUR package pin a sha256 of the exact release asset. The signing key lives only in the `GPG_PRIVATE_KEY` CI secret and the maintainer's keyring — `*.asc` is gitignored so an exported half can never be staged. Details in [Installers & Packaging §9.1–9.3](09-Installers-and-Packaging.md).
- The infrastructure stack has its own hardening (per-IP quotas on claims and browser connections, rate limits, STUN without relay, non-root containers, no published API port) — see [Infrastructure Stack §10.12](10-Infrastructure-Stack.md#1012-hardening--limits).
- **The bootstrap is the one piece of this project's code a browser loads from a server**, so it is kept small enough to read and compared on a schedule against a reference copy published elsewhere — [Infrastructure §10.8](10-Infrastructure-Stack.md#108-the-bootstrap-entry-page), including what that comparison does *not* catch.
- Backend security-focused tests exist (`backend/tests/security_main.cpp`, `test_auth_manager.cpp`, `test_connection_guard.cpp`, `test_input_crypto.cpp`).
