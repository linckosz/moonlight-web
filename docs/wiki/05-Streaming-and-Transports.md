# 5. Streaming & Transports

This chapter explains how video, audio and input actually travel between Sunshine, the MoonlightWeb server and the browser — the heart of the project, and where most of the hard-won engineering lives.

## 5.1 The five transport modes

The same Sunshine-side stream (RTSP/RTP/ENet handled by `moonlight-common-c`) can be relayed to the browser in five ways:

| Mode | Backend relay | Browser path | Video sink | Codecs | Notes |
|---|---|---|---|---|---|
| `webrtc-dc-udp` | `DataChannelRelay` | video+input SCTP DataChannels **+ RTP audio track**, UDP ICE | canvas (WebCodecs) | H.264/HEVC/AV1 | Default. Lowest latency with full codec choice |
| `webrtc-dc-tcp` | `DataChannelRelay` | same, ICE-TCP candidates | canvas | H.264/HEVC/AV1 | UDP-hostile networks |
| `webrtc-media-udp` | `MediaTrackRelay` | RTP video+audio tracks, input DataChannel | `<video>` (browser decoder) | **H.264 only** | Browser-managed jitter/FEC/PLC; true-HDR-capable sink |
| `webrtc-media-tcp` | `MediaTrackRelay` | same, ICE-TCP | `<video>` | H.264 only | |
| `wss` | `StreamRelay` | one WebSocket (TLS), video+audio+input multiplexed | canvas | H.264/HEVC/AV1 | **LAN IP only, not user-selectable.** Rides the TLS connection that served the page, so it exists only for a browser opened directly on the host's LAN address; worst latency profile |

The two WebRTC families differ only in the **video** path: `-dc` fragments access units over SCTP for WebCodecs, `-media` sends a real RTP video track. Audio is an RTP Opus track in both; input is always the `input` DataChannel. `-udp` vs `-tcp` changes nothing but the ICE candidate types (`enableIceTcp`).

### The fallback chain

`TransportPriorities::orderedTransports()` defines the auto order:

- **Video Enhancement OFF**: `webrtc-dc-udp` → `webrtc-dc-tcp` → `webrtc-media-udp` → `webrtc-media-tcp` → `wss`
- **Video Enhancement ON** (canvas required for WebGPU): `webrtc-dc-udp` → `webrtc-dc-tcp` → `wss` → `webrtc-media-udp` → `webrtc-media-tcp` (media kept only as a last resort, streaming *without* enhancement)

`wss` is dropped from the chain for any browser that arrived through the rendezvous (`req.viaTunnel`) — there is no page-serving TLS connection to carry it. Since that is how every user reaches the app, the rung is effectively LAN-IP-only, and the admin selector omits it outside debug builds (`available_transports`). Selecting it by name is still honoured, and still reported: the `/start` response carries `transport_dropped` and the browser shows which transport actually runs. Since 0.4.1 the `-tcp` rungs cover most of the UDP-blocked case that `wss` used to, through passive ICE-TCP: see [Networks that let no UDP out](#networks-that-let-no-udp-out).

Rules applied when building the chain (`main.cpp`):

- HEVC/AV1 requests **skip webrtc-media** (H.264-only) — or, if a media mode is explicitly forced, the codec is overridden to H.264 and the response flags `codecOverridden` + `originalCodec`.
- Host codec support is checked against the canonical `SCM_MASK_*` values from `Limelight.h` (the GFE-era literals are wrong for Sunshine).
- A forced `-udp` mode promotes its `-tcp` sibling to second place (same family before switching).

**The browser owns the loop**: the `/start` response is sent *before* ICE connects, so only the client can observe a connection failure. The full `transport_chain` and current `transport_index` are echoed in the response; on failure the frontend relaunches with `transport_index + 1`. Manual transport selection precedes automatic fallback.

**Only a transport failure costs a rung.** A `/start` that never yields a session — timeout, 502, Sunshine refusal — is a verdict on the host, not on the transport: nothing was offered, no ICE was gathered. It is retried once on the *same* index and then reported as such (`transport.launchFailed`). Charging it to the chain empties the ladder against an unresponsive host and ends on a "no transport works" that is simply false — the 2026-08-07 incident, where a wedged Sunshine consumed all three rungs in 60 s without a single ICE attempt. The worker's own launch deadline (`NvHTTP::LAUNCH_TIMEOUT_MS`, 20 s) is deliberately shorter than the browser's `/start` timeout (25 s) so the failure is *reported* rather than the worker being killed mid-request by the relaunch that takes its slot.

### Networks that let no UDP out

A school, an office or a guest Wi-Fi that blocks outgoing UDP usually still lets TCP out, and since 0.4.1 the entry link and the stream go over it, **still direct, never through a relay**. ICE-TCP needs one side that listens. libjuice (1.7.1) only does *active* TCP — it dials, it never listens — and so does Chrome: it has active TCP candidates (port 9, visible in `getStats`) that it never signals, and it dials a *passive* candidate the moment it is given one (checked on 23/10/2026). Our libjuice patch makes the host listen as well (`ice_tcp_passive`, on by default since 0.4.1). While their ICE checks run, the tunnel and the `-tcp` rungs offer a passive candidate on their port's TCP side, which `RouterPortCore` maps beside the UDP hole. The listener keeps nothing that has not authenticated with the session's ICE credentials, and closes when ICE ends ([design](../design/ice-tcp-passive.md)). The browser's STUN probe finds no UDP, the `-udp` rungs are skipped (below), and the stream runs on `webrtc-dc-tcp`. Checked on 26/10/2026 from an office network, with the bench key `debug_ice_drop_udp` keeping every UDP candidate out: tunnel and stream over TCP, two minutes at 52-60 fps without a gap, 24.7 ms end to end.

Two cases still end on *"Your machine answered, but no direct connection could be opened"* (`noRouteError` in `bootstrap/v1/tunnel.js`):
- a network that lets TCP out on 80 and 443 only. The host's ports are high: 3478-3481 and 5349-5352 then 46000-46031 for the tunnel, 48550-48573 or 46100-46199 for the media;
- a Linux host whose ufw or firewalld opens only the UDP ports, as the packages do: the browser's TCP connection is refused before it reaches the listener.

The project runs no relay (no TURN), so that is the expected outcome, not a fault.

**For those, the way around it is the host's direct address, `https://<public IP>`**, the one place `wss` still runs: the page and the stream then share a single TLS connection to the host on TCP, which such networks usually let through on 443. Verified on 22/10/2026 from an iPhone on 5G, owner and invited player, with `wss` forced too. What it takes:

1. **Forward a TCP port by hand on the router**, external 443 → the host's `https_port` (443, or the port it fell back to). UPnP maps media and tunnel ports, never a web port. The public IP is shown under Admin › Internet, on the host machine itself only: it is redacted for any request that is not local, the tunnel's included.
2. **Accept the certificate warning.** The host serves its self-signed certificate under an address it has no name for. Accepting it trusts whatever answers on that address; the PIN, not the certificate, is what admits.
3. **Pair again.** The direct address is another origin from the entry link: no session, no pairing key carried over. The owner enters a PIN from the admin page. An invited player opens `https://<public IP>/p/<token>` — the token is what follows `#t=` in the shared link, which the interface does not print in this form — and enters the invitation's PIN.
4. **Wait for the chain.** The browser's STUN probe (`api/UdpProbe.js`) finds no UDP and the start request says `udp_blocked`. For a browser planned for the internet, `dropUdpRungsWhenBlocked` (`main.cpp`) then removes the `-udp` rungs, and only those: the one or two `-tcp` rungs still run to their ICE deadline (8 s each in the 22/10 bench) before `wss` takes over. The first frame can take about twenty seconds. A player's chain ignores the owner's forced transport.

What it costs: the link carries the home's public address in clear, and a dynamic IP breaks it at the next change. `wss` is also the worst latency profile of the five, with TCP head-of-line blocking under loss. Putting `wss` back under the entry link would need a valid certificate for that address, so a name per user, which the project does not issue ([Security §6.5](06-Security.md#65-tls)).

## 5.2 Video path

```
Sunshine GPU encoder ─RTP/UDP─► moonlight-common-c ─decoded access units─► MoonlightShim
    ─► Relay (DC: FrameSender thread / media: RTP packetizer / WSS: WS frames)
    ─► Browser: reassemble → WebCodecs VideoDecoder → renderer (WebGPU/2D canvas or <video>)
```

Key mechanics (all present in the code — regressions here are the most expensive class of bug):

- **Frame framing (DC/WSS)**: each access unit is fragmented into DC messages with a header carrying a `frameId`. The video DC is **ordered** with `maxPacketLifeTime=500 ms` (a lifetime, not a retransmit count: a link freeze must not replay second-old frames ahead of the keyframe); the frontend detects `frameId` gaps and requests an IDR rather than reordering (a frontend reorder buffer was tried and removed — it causes IDR floods and latency).
- **IDR discipline**: IDR requests are throttled/coalesced backend-side (250–500 ms cooldown, sticky `m_AwaitingIdr`), and both sides apply **exponential backoff** under congestion — otherwise mobile networks enter an IDR spiral.
- **Backpressure everywhere**: a DC send backlog bounded in time, not bytes (`SendBacklog`), frontend consults `decodeQueueSize` before `decode()`, bounded worker→main signal queue (`m_PendingVideoFrames`, decremented on consume), WebGPU `draw()` awaits `onSubmittedWorkDone()`.
- **webrtc-media specifics**: the track declares its SSRC, so the browser's NACKs and PLIs reach the backend (a throttled `PliHandler`); RTP timestamps are derived from real capture times (a synthetic 60 fps clock broke frame pacing); packets are sent from the capture thread; `playoutDelayHint`/`jitterBufferTarget` is set on the `RTCRtpReceiver` (not the element), driven adaptively by `JitterController` (AIMD; a non-zero target also re-arms backend NACK).
- **DataChannel presentation pacing**: the DC/WebCodecs path has no dejitter buffer of its own — it presents on decode and drops to the freshest frame, so link jitter becomes "repeat + skip" judder (a visible 2–3 frame hitch at unchanged mean RTT). `FramePacer` (**opt-in**, `mw_pacing=1` — the project rule is freshest-frame-first: on real Wi-Fi, power-save delivers frames in 20-40ms bursts, so the p95-sized reserve legitimately sits near its cap and the latency it buys back is the project's priority) rebuilds the reserve from the `backendTs` capture stamps: it tracks the minimum transit delay, sizes the reserve at p95 of the per-frame excess, and stamps each decoded frame with a presentation deadline (rise immediately, decay slowly, hard cap 25 ms — deliberately tight: past ~1.5 frames the added lag hurts a shooter more than the judder it removes). At target 0 — the clean-link state — the behaviour is bit-for-bit the old immediate path. **The quantile is the whole control law**: it covers the tail and deliberately lets outliers hitch. The underrun fast-path (`noteUnderrun`) may only bring the target to that same quantile sooner, never past it, and must not touch the decay clock — a version that did both shipped briefly and pinned the reserve at the 25 ms cap on every non-loopback link (24.6 ms held against a 2.9 ms measured tail), because a few percent of late frames bump faster than the decay sheds and reset the decay timer on the way. The hold shows up in the existing render-queue latency leg, so it is never hidden from the overlay. Applies to both the worker and main-thread paths; **not** to webrtc-media, where the browser's own buffer does the job (see `JitterController` above).
- **Codec bootstrap**: SPS/PPS(/VPS) are parsed browser-side (`Mp4Muxer.js` / `Av1Utils.js`) to build exact codec strings for `VideoDecoder.configure`; 4:4:4 chroma is opt-in and only offered for profiles the selected codec/browser advertises via the codec masks.
- **PyroWave (Wired LAN only)**: the intra-only wavelet codec of POC Ultra (`docs/design/ultra-lan-poc.md` §6.43), chosen in a browser's Settings and asked as `ultra_codec` at `/start`. Only a native Windows host codes it (D3D12 route, `NativeHostBackend::pyrowaveSupported`, announced on its card), only on the DataChannel transports, 8-bit SDR. Its frames ride the audio road (`native:…+aroad`) in 1,400-byte chunks, and the page decodes them itself on its main thread (`stream/ultra/UltraPlayer.js`): WebGPU, or WebGL2 where no adapter answers (Chrome on Linux, Safari 18). Never a guest's, never chosen by Auto; a choice that cannot run streams HEVC (`util/PyrowaveCodec.js`).

### Why canvas *and* `<video>`?

- **Canvas (WebCodecs decode)** gives frame-level latency control, codec freedom (HEVC/AV1), custom rendering (WebGL2/WebGPU upscaling/sharpening) and precise stats. It is the default sink, and the fastest one measured: the `<video>` element presents on the compositor's vsync behind its generator's queue and came out 35–45 ms slower click-to-photon in every series ([ch. 15](15-Client-Presentation-Benchmarks.md#155-decision-4--hdr-routing)).
- **`<video>`** is used in two situations: (a) the *webrtc-media* transport, where the browser owns decode and dejitter entirely; (b) the `VideoElementRenderer` sink on the DC transport for **HDR with HEVC**, the one case where no canvas can carry the HDR signal (below).

## 5.3 HDR — support and limitations

- The stream can be encoded HDR10 (HEVC/AV1, `hdr_enabled`); decoded `VideoFrame`s carry the bt2020/PQ `VideoColorSpace`. The Sunshine/GameStream hosts encode it, and so does the native host from a display in HDR mode (Windows, macOS 15), never on Linux.
- **The constraint**: on any canvas, `importExternalTexture` (WebGPU) and `drawImage` (Canvas2D) tone-map a PQ frame to SDR **on import** — on Chromium. The HDR signal survives only through `VideoFrame.copyTo()` of the raw planes, and `copyTo` works on **software-decoded** frames only — Chrome has a software AV1 decoder (dav1d), no software HEVC. WebGL2 and Canvas2D have no HDR surface at all in Chrome. **WebKit does not tone-map on import at all**: it hands back the raw PQ code values, which painted as sRGB give the washed-out grey picture seen on iOS — hence the `tonemap-ext` path below.
- **Routing** (`_hdrMode` in `StreamView.js`, decided from the Enhancer setting, the codec and the display; the display answer is live via `matchMedia('(dynamic-range: high)')`). The Enhancer needs the frames in the shader pipeline, which the `<video>` sink bypasses — so the sink wins when no Enhancer was asked for, a tone-map when one was:
  - **Enhancer off** + HDR display + a track generator → `sink`: `<video>` via `MediaStreamTrackGenerator` (Chromium) or `VideoTrackGenerator` (WebKit), hardware decode, true HDR.
  - HDR display + **AV1** → `linear`: `rgba16float` WebGPU canvas in extended tone-mapping mode, PQ → scene light (203 nits = 1.0), BT.2020 → P3; the Enhancer runs in HDR. True HDR.
  - SDR display + AV1 → `tonemap`: ACES HDR→SDR in the renderer's first pass from the `copyTo` readback, Enhancer on a normal canvas. `mw_hdr_tonemap=1/0` forces / disables it; `mw_hdr_curve` / `mw_hdr_exposure` / `mw_hdr_refwhite` tune it.
  - **WebKit, any codec** → `tonemap-ext`: the same ACES first pass, fed by `importExternalTexture` instead of a readback (the browser has already applied the YUV→RGB matrix; the shader does PQ EOTF → gamut → curve → sRGB). Needs no software decoder, so it is the only tone-map available for HEVC, and the Enhancer survives. `mw_hdr_ext_tonemap=1/0` forces / disables it.
  - no sink and no tone-map → `browser`: plain blit, the browser's own tone-map on import.
  - **A browser that hands opaque frames** (no format, no `copyTo`): Chrome and Safari on an Apple-silicon Mac decode AV1 in hardware whatever they are asked (26/10/2026). The stream checks its first HDR frame; an opaque one is remembered for that browser version, 30 days at most, and the stream comes back once on a route without the readback: on WebKit in HEVC through `tonemap-ext`, the Enhancer kept; elsewhere in AV1 through the `<video>` sink on an HDR display, or the browser's own tone-map on an SDR one. A browser that does not know the canvas's `toneMapping` (Chrome before 129) takes `tonemap` instead of `linear`, rather than a float canvas clamped at white.
- **Guard**: the HDR checkbox is offered only when the client has an HDR display **and** a WebGPU adapter **and** a 10-bit decoder (`hdrClientCapability()`); otherwise it is greyed with the reason and the launch omits `hdr_enabled`. `mw_hdr_request=1` bypasses the guard for experiments.
- Practical consequences: **HDR and the Enhancer are compatible on AV1** (and on WebKit, at SDR fidelity), exclusive on HEVC under Chromium, which is why the **Auto** codec, the default since 0.4.1, takes AV1 for an HDR stream with the Enhancer; true HDR costs about 10 ms more than SDR on this client (software AV1 decode + float canvas); **HDR is 4:2:0 only** — HEVC 4:4:4 10-bit decodes but renders green on Chrome/Windows ([ch. 15 §15.6](15-Client-Presentation-Benchmarks.md#156-decision-5--444-chroma)).

## 5.4 Audio path

```
Sunshine ─RTP─► moonlight-common-c (Opus packets, NOT PCM) ─► relay
   webrtc-dc / webrtc-media: native RTP Opus track → browser (jitter buffer + FEC/PLC) → <audio>
   wss                     : Opus over the WebSocket → WebCodecs AudioDecoder → AudioWorklet (jitter buffer + WSOLA)
```

- **Both WebRTC transports carry audio as a real media track, never a DataChannel** — `m=audio` sendonly, Opus PT 111, `OpusRtpPacketizer` + `RtcpNackResponder(64)`, played from `pc.ontrack` on an `<audio>` element. `DataChannelRelay` and `MediaTrackRelay` are identical here. The ordered audio DataChannel this replaced head-of-line-blocked on packet loss (periodic ~0.5 s dropouts); the browser's NetEq conceals the loss instead. SCTP id 1 stays reserved-but-unused from that era.
- RTP timestamps advance by the negotiated Opus frame size (`audioSamplesPerFrame()`), never by arrival time — an arrival-time clock makes NetEq time-stretch and the audio turns robotic.
- Stereo Opus (the native host encodes two channels; a 5.1 endpoint keeps its front pair); SDP carries `stereo=1;sprop-stereo=1` (without it libwebrtc instantiates a **mono** decoder and downmixes (L+R)/2 — ~6 dB quieter than moonlight-qt, stereo image lost). Mobile clients may request 10 ms low-bandwidth frames (`low_audio`).
- **`wss` only**: `AudioPipeline` decodes Opus with the WebCodecs `AudioDecoder` (WASM `opus-decoder` worker fallback) and feeds `audio-processor.js`. That AudioWorklet jitter buffer adapts between ~60 and ~160 ms; WSOLA time-stretch (default on) absorbs clock drift pitch-free.
- `mute_host_audio` maps to GameStream `localAudioPlayMode` (host speakers muted by default while streaming); the native host honours it too, on Windows, Linux and macOS (`HostMute`); on Windows by muting an output that mutes in hardware or routing to a virtual sink — see the design doc §24 for why a software mute cannot be used.
- **Native host** (`mw-native-host`, Windows, Linux and macOS): the capture is WASAPI **loopback** of the default output on Windows (its own MMCSS "Pro Audio" thread, which waits on the device and on the 5 ms tick together), PipeWire on Linux, ScreenCaptureKit on macOS (both push PCM into `PacedOpusSink`, which owns the tick there) → `AudioPacer` (exactly one 5 ms frame every 5 ms; a frame not yet captured is waited for up to 5 ms of grace before silence takes its place — without that grace a Windows host put a few ms of silence in, one to four times a second under music, the crackles fixed on 12/10/2026; oldest frames dropped past the queue's cap, so the fixed-increment RTP clock above stays true) → libopus 1.5.2, restricted low-delay (CELT), 128 kbps constrained VBR (digital silence costs 3 bytes a packet). No in-band FEC: it is a SILK feature, impossible at 5 ms; loss is the browser's PLC plus the RTP NACK responder. The browser's NetEq buffer sizes itself: since `b169a217` no `jitterBufferTarget` floor is set (it acts as a minimum, and the old 60 ms cost Chrome on a Mac 37 ms on every sound); `localStorage.mw_audio_target` = ms or `off` sets one for a bench. The **"Audio buffer"** row of the latency breakdown (both WebRTC transports, `getStats` interval delta of `jitterBufferDelay`) is shown and never added to the video total: no video frame ever waits for audio, so the sound trails the picture by about that buffer. Bench trap: a client running on the host loops the stream's own playback back into the capture.
- **Packet priority (DSCP)**: the native host and the relay send audio, video and every DataChannel in **AF41**, the Wi-Fi's video queue (WMM), on Windows, Linux and macOS alike — `streaming/PacketMarking`, through a `.patch` on libdatachannel (`rtc::SetDscpSettings`) and two on libjuice: on Windows, one that lets an unelevated socket set `IP_TOS`; on macOS, one that sends the class with each packet to an IPv4 peer, which macOS otherwise leaves unmarked on a dual-stack socket. A single class on purpose: one SCTP association carries one DSCP, and audio in EF measured nothing yet. Admin › **Give the stream priority on the network** (`packet_marking`, default on) turns it off for a house whose other devices suffer while a stream runs; the next stream reads it. `MW_DSCP=a,v,d` overrides per class for a bench. Measurements: `docs/design/network-latency-findings.md`.
- **The viewer's microphone rides the same audio section, the other way** (Settings › *Send my microphone*, `/start`'s `mic_enabled`). The session grants it only when the host is this machine (the native host, or a Sunshine on the same PC — GameStream has no microphone channel to a remote one) and the viewer is the owner; it then opens the device first (`MicUplink`, `MicOutput*`) and both WebRTC relays offer `m=audio` **sendrecv** instead of sendonly — no second track, no renegotiation — with `maxaveragebitrate=128000;maxplaybackrate=48000` added to the Opus fmtp, the ceiling the browser's encoder takes as its target. The `/start` reply says `mic: true`, or `mic: false` with `mic_why`; only on `true` does the page call getUserMedia, answer the section sendrecv, `replaceTrack` its track onto it and set the sender's `maxBitrate` (`audio/MicUplink.js`), so no permission is asked for a microphone that would lead nowhere. **Two qualities** (Settings › *Microphone sound*, `mic_quality`): `voice`, echo cancellation + noise suppression + AGC at 64 kbit/s, and `clean`, none of the three at 128 kbit/s. Measured in Chromium (fake 440 Hz microphone, 29/10/2026): the old offer already got 65 kbit/s (its `stereo=1` moves Chrome to the stereo default), and a steady tone came through voice processing ~19 dB down; `clean` sent 129 kbit/s and the tone arrived at its own level. The processing, not the codec, is what thinned the voice. **On the WebSocket transport** (`wss`, what a tunnel without UDP leaves) there is no track to answer: the page captures 20 ms frames in an AudioWorklet (`audio/mic-capture-processor.js`), encodes them with WebCodecs' Opus `AudioEncoder` at the quality's bitrate, or sends 16-bit PCM without one (768 kbit/s), as `[0x4D][codec][seq:2][payload]` binary messages on the stream's socket (`audio/MicSocketSender.js`), dropping a frame while the socket holds more than 128 KB; `StreamRelay::onWsBinaryMessage` hands them to `MicUplink::onSocketFrame` (`MicRtp.h` parses the framing). Same ring and device from there; nothing to conceal on a reliable socket. Mute disables the track (Opus silence keeps flowing, the host's device stays where apps found it). A standby leg holds its microphone until it is promoted, or the host would hear the voice twice during a seamless switch. On the host: `Track::onMessage` hands over the track's RTCP as plain binary too, told apart by RFC 5761 (`MicRtp.h`); libdatachannel routes the RTP by SSRC alone, so a sending answer without `a=ssrc` delivers nothing (the relay logs which case it got). Opus is decoded mono at 48 kHz — in-band FEC for a single lost packet (`useinbandfec=1` in the offer asks the browser for it), PLC for up to 10, nothing across a longer gap — into a ring that primes 40 ms, goes silent and primes again when dry, and trims back to 40 ms past 150 ms (`MicJitter.h`): no time-stretch, latency over smoothness. **Windows** plays it with shared-mode WASAPI (event-driven, MMCSS "Pro Audio", the device's own channel count, the engine converting the rate) into the render side of a virtual cable — VB-CABLE's *CABLE Input*, Steam's *Steam Streaming Microphone*, or `mic_device`; never a real output and never *Steam Streaming Speakers*, which Sunshine captures. **Linux** makes a PipeWire `support.null-audio-sink` with `media.class = Audio/Source/Virtual` and `object.linger`, *MoonlightWeb Microphone*, once, and links a playback stream into it per session by hand (`link-factory`, once the session manager has given the stream its port): WirePlumber 0.5 answers *no target node available* to a playback stream aimed at a virtual source, and the hand-made link can never fall back to the speakers. The device outlives the worker, so an app keeps it across relaunches and quality switches. libpipewire is opened through a private function table, since the native host's `pw_*` forwarders live in the same binary. macOS: not yet.
- **Never apply gain in JS** — the historical "60% volume" issue was Sunshine's virtual sink volume on the host (host loopback is post-volume and volume keys act on it mid-stream); `HostAudioSink` normalizes it.

## 5.5 Input path

```
Browser events (kbd/mouse/touch/gamepad/clipboard)
  ─JSON over input DC (or WSS)─► backend InputEncoder (binary Limelight packets)
  ─InputCrypto AES-128-GCM─► EnetControlStream ─ENet─► Sunshine
```

- **Scroll is counted in WHEEL_DELTA units (120 to a notch)**, never in browser pixels — the client normalizes `deltaY`/`deltaX` (deltaMode-aware) and carries the fractional remainder between events, because the backend parses the value with `QJsonValue::toInt()`, which returns 0 for a non-integer. What happens next **depends on the host's OS**, and the two cases want opposite things. **Linux throws away anything under a notch**: inputtino emits `REL_WHEEL = amount / 120` with no accumulator, so only the `REL_WHEEL_HI_RES` companion event can save a trackpad or a touch drag, and X11 sessions routinely ignore it. **Windows and macOS keep the leftovers** — `SendInput` accumulates, and libvirtualhid's macOS backend scales to CoreGraphics pixels before dividing — so holding amounts back for them is a real loss: it turns a trackpad or a high-res wheel into a ratchet. There is no wire value that suits both, since a host counting whole notches needs events of at least 120 and smoothness needs events well under it. So `MoonlightShim::quantizeScroll` (one carry per axis, alive for the session) runs **only for a host we believe drops them** — the same thing Sunshine's own `high_resolution_scrolling = disabled` does, decided per host and covering every client and every input path at once.
- **Which OS a host runs is worked out, never asked for** (`HostOsProbe`). Nothing on the control plane says: `serverinfo` carries no OS field (see `BackendProbe.h`), and Sunshine's management API answers 401 to `/`, `/api/config` and `/welcome` without credentials — `/api/configLocale` is the one unauthenticated endpoint and it returns only a locale. What is left is a handful of facts that each imply an OS: the host resolves to **this machine** (then it is our own OS, at compile time); its backend identified itself as **Wolf** (Linux containers only) or **MultiSeat** (Windows sessions); it is the **NVIDIA original** (`MJOLNIR`, Windows-only); or the **IP TTL** its own packets arrive with. Stacks start the TTL at 128 (Windows) or 64 (Linux, macOS) and each router lowers it by one, so a TTL above 64 proves Windows — while 64 does **not** separate Linux from macOS, which want opposite handling, and so is left Unknown rather than guessed. An unidentified host is quantized: a dropped notch is a feature that does not work, a chunky notch is one that works less smoothly.
- **The TTL is read off the media path**, which is the only place a host's own packets reach us — nothing on the control plane answers over UDP. `moonlight-common-c` (our fork) sets `IP_RECVTTL` on every UDP socket it binds and reads the TTL off the first datagram with `recvmsg`/`WSARecvMsg`, exposing it as `LiGetHostIpTtl()`; every packet after the sample goes through plain `recvfrom` as before. The session polls for it for the first few seconds and re-decides quantization live if it settles an OS that was Unknown at launch, then reports it to the parent so the next session starts out knowing. It is **never persisted** — the bench-mini dual-boots, and a remembered TTL would name the wrong system half the time — and it never overturns a stronger verdict.
- **The Linux side of this belongs upstream** and a ready patch is in `docs/upstream/inputtino-scroll-remainder.patch`: keep the sub-detent remainder in inputtino, which is what LizardByte's libvirtualhid already does (`accumulated_legacy_scroll()`). Sunshine adopted libvirtualhid in `v2026.830.44125`; every release up to `v2026.516.143833`, and Wolf, still use inputtino. The local workaround cannot be dropped until the fix reaches the builds people actually run.
- **Input messages are JSON, on purpose.** Measured on the host (Qt 6.10.3, `/O2`): parsing and dispatching one message costs 0.65 µs (relative mouse move) to 1.6 µs (gamepad snapshot) — a millisecond of CPU per second at 1000 Hz. A binary wire format would save microseconds on a millisecond budget, so there is none. What matters is *when* the message leaves the browser, below.
- **Mouse at the device's report rate.** `mousemove` is dispatched once per display frame with the motion since the previous one summed: a 1000 Hz mouse on a 60 Hz screen reaches the host as 60 messages a second, each up to 16 ms late. The view listens to `pointerrawupdate` instead (Chromium; every device report, off the frame clock) and the mousemove handlers keep only their cursor bookkeeping. The **native host** injects each event on the libdatachannel thread that received it, so the extra messages buy the delay back. **GameStream hosts** (Sunshine, Wolf, Apollo, MultiSeat) get the same since 13/10/2026: moonlight-common-c sums the moves and sends them at most every millisecond, so the host is not flooded, and an in-game A/B towards Sunshine at 120 fps felt no difference either way (with a 125 Hz mouse, slower than the screen, the rate cannot gain anything) — the mode meant to be fastest became the default. Browsers without the event keep the frame cadence. `localStorage.mw_raw_pointer = '0'`, read when the stream starts, goes back to the frame cadence towards every host. With `mw_perf_diag=1` the `[perf]` line shows the mouse's messages per second, a report's age when it leaves (`performance.now() - event.timeStamp`), the interval between sends, and `wait` = age + interval/2, the average delay to compare between the two modes.
- **Pads are read at 250 Hz, whatever the host.** A gamepad sends no events: a button is only seen when the page reads `navigator.getGamepads()`, and Chrome samples pads at 250 Hz. Read once per display frame, sticks and buttons alike waited ~8 ms on average at 60 Hz. `GamepadManager` keeps its rAF loop, which finds the pads, and adds a 4 ms timer while a pad is forwarded, the page visible and the stream not paused. A message still leaves only when the state changed, plus a repeat every 500 ms, so a pad sends at most its own report rate (a TX12 radio: ≤ 197 updates/s), about 30 KB/s at 250 a second. Measured in Chrome 154: 16.7 ms between two reads before, 3.6 ms after (p95 4.8 ms). With `mw_perf_diag=1` the `[perf]` line shows `pad read N/s sent N/s gap p95/max`.
- **The receiver tells the native host what the link is doing** (`linkstats`, twice a second on the input channel, DataChannel transport; the media transport's `clientstats` RTP counters feed the same input). The signal is the *rise of one-way delay*: every frame carries the host's present time, so the client measures how much later frames arrive than at the best of the session — the queue building in the transport, in milliseconds, seconds before anything is lost (the two clocks' offset cancels in the subtraction; a 30 s rolling reference absorbs drift) — plus frame-number gaps. The host cannot see any of this: on its side a saturated link looks like frames leaving on time into a megabyte of SCTP buffer. The native engine's rate governor cuts the encoder's bitrate 20 % the moment the delay rises (or a gap, or one of its own sender's evictions), holds two seconds, and climbs back 5 % per quiet report, never above the setting, between two frames with nothing renegotiated — so the app's degradation ladder stands down for the native host. GameStream hosts keep the ladder. On Windows the governor also reads the relay's own SCTP counters and cuts as soon as more than 3 ‰ of the chunks sent in the last half-second were retransmissions (`retrcut`): on Wi-Fi that is the earliest sign a burst overflowed the client's socket, often before the delay rise shows. Linux and macOS keep it off — measured without effect there.
- **The native host sends without a burst limit** (Windows, Linux and macOS): usrsctp's `max_burst` (libdatachannel sets 10) caps how many packets leave per SACK, so a 16 KB chunk queued behind a large frame waited up to ~15 ms in the stack on a Wi-Fi client. `max_burst = 0` let the congestion window decide alone: click-to-flag −8 ms on a Wi-Fi Mac client, frame age −4.6 ms on Ethernet, never worse. The SCTP send buffer, for the record, is not the 64–256 KB once assumed tunable — libdatachannel sets `SO_SNDBUF` to `maxMessageSize` (256 KiB), and shrinking it (`sctpbuf=`) only capped throughput: a byte stays ~16 ms unacknowledged. Measurements and dead ends: `docs/design/network-latency-findings.md`.
- **A lost frame is healed with a delta on the native host** (`invalidateref`). When `/start` says `ref_invalidation: true` (NVENC, which keeps a four-frame DPB and accepts `NvEncInvalidateRefFrames`), a frame-number gap no longer closes the reference gate: the client names the missing wire ids to the host and keeps decoding; the relay maps them to the engine's frame numbers (a ring of the last 512, since the two drift apart at every frame the relay drops) and the encoder predicts the next pictures from frames the receiver has. A hole wider than the DPB, an unmapped id, or an encoder without the feature (AMF, oneVPL) falls back to the keyframe path as before. Debug hook: `localStorage.mw_drop_test = N` discards one delta every N frames on the client, to exercise either path on a link that never loses anything.
- Mouse: relative (pointer-lock) or absolute; scroll (vertical + horizontal — the latter is a Sunshine-only extension, silently ignored by GFE hosts), buttons. Touch: trackpad translation (1/2/3-finger gestures), or absolute touch-screen mapping when `touch_screen` is on. Keyboard: raw key events, Escape is a normal key; a printable key also carries the character the client's layout produced and the mouse mode it was pressed in, and `keyboard_layout_fidelity` decides between the two ([Settings §7.2](07-Settings-Reference.md#72-key-reference)). Text from a phone's keyboard (`textinput`) reaches a **Windows native host** as the keys of the host's own layout (`input/windows/WinTextKeys`): the classic console ignores a character injected as Unicode, and games see keys. Each key is read back through the layout with Caps Lock, a character it reaches through a dead key goes as the dead key then its base, and Unicode stays for what no key types (an emoji) and for an open input method. AltGr goes as a keyboard sends it, the left Ctrl and the right Alt: Windows Terminal reads a left Ctrl+Alt+digit as its tab shortcuts. An Alt let go or put back alone is masked by an unassigned key (0xE8), so Windows never takes it for a tap of Alt that opens the menu bar. A physical key's levels go back with its press, so keys rolled over each other keep their case. In a shortcut, a letter is the key the layout calls by it, under the modifiers held. Gamepads: `gamepadconnect`/`gamepad`/`gamepaddisconnect` snapshots + rumble back-channel. Wheels and radios as themselves (native host): `hidattach`/`hiddetach` on the input channel, reports on an unordered `hid` DataChannel, force feedback back as `hidffb` ([§4.9](04-Frontend.md#49-wheels-and-radios-as-themselves)).
- **Lock-key sync is host-authoritative**: on the first keydown the client sends `locksync`; the backend reads the *real* host state (`GetKeyState`, gated to host==backend) and reconciles — never a blind NumLock tap. The sync runs synchronously on the relay thread to preserve input ordering. When the host is remote its state is unreadable, and the fallback is each lock's hardware default — **NumLock on**, Caps and Scroll off. That default is load-bearing on Linux hosts: Sunshine turns VK_NUMPAD1 into evdev `KEY_KP1`, which xkb reads as End whenever the host's NumLock is off, so presuming "off" tapped an already-aligned host and left the guest with a cursor pad instead of a numpad. Windows hosts are immune — Sunshine injects the VK there and never consults the lock state.
- **A Windows host with no pointing device** (a mini-PC, a living-room PC) draws no pointer: `GetCursorInfo` says hidden, without even a cursor handle, so neither the capture nor the client has one to show (Parsec shows none either), and a game that reads Raw Input by device finds none to read. The **native host** gives such a host **a mouse of its own for the stream**: at `start()`, when Raw Input lists no mouse, `Win32Input` makes one through the **MoonlightWeb Virtual HID** driver (0.1.2.0 or later, x64), with the fixed descriptor of `input/SystemMouse.h` (5 buttons, 16-bit relative X/Y, wheel and horizontal pan), the one mouse the driver takes, byte for byte: a page's forwarded device can never be it, since `hid::validate()` still refuses mouse and keyboard collections. Windows then shows its pointer, and games read a device (Portal 1 on the N95 bench, 20/10/2026). Relative moves go through it, and so do the buttons and wheels while the viewer moves relatively (gaming mode, a game that re-centres); an absolute position stays `SendInput`, and so does a click right after one, since a HID report travels the HID stack and would land after a `SendInput` sent at the same moment. A button is released the way it was pressed. A report the device refuses lets the mouse go, with what it held, and input carries on through `SendInput`. The mouse lives as long as the session: `stop()` removes it, a worker that dies takes it with it, and the host is back to no pointing device (no parking between two streams, unlike a forwarded wheel). Two streams on the same host make one each. `vmouse=` in the native tuning chooses: `-1`, the default, only on a host with no mouse; `0` never; `1` always, beside a real mouse too, for the bench.
  - **Fallback, Mouse Keys**: where the mouse cannot be made (no driver or an older one, Windows on ARM, a worker that is not elevated), or is still not listed by Windows 3 s after it was made, the native host turns Windows' **Mouse Keys** on for the stream when `SM_MOUSEPRESENT` is 0 (`core/PointerPresence.h`), as Sunshine does: they count as a pointing device, and the pointer shows within two seconds (N95 bench, 16/10/2026), but games get no device to read. On, available and at the slowest speed only — no notification-area icon, no sound, no hotkey — and for the session only: never written to the profile, so signing out clears them whatever happens. Re-checked every second (a mouse unplugged mid-stream, a second stream on the same host), left alone while the stream's own mouse shows the pointer (`IInputSink::showsPointer()`), and put back exactly at the end unless the user changed them meanwhile. A worker that dies holding them has them put back by the server (`mouseKeys` event, `restoreMouseKeys`), except a server running as a service, outside the console session: there they last until sign-out. The cost, on such a host and during the stream only: with NumLock off, the numeric keypad moves the pointer and its 5 clicks.
- **A stall must not stretch a keypress** — the input channel is ordered+reliable, so a freeze does not lose events, it *delays* them: a press that already landed stays down for the whole stall while its release waits in the SCTP queue, and guest typematic turns one keystroke into dozens (2 s freeze ≈ 45 `r`). Nothing the client sends during the stall can fix that (the correction rides the same blocked queue), so the host side runs a **dead-man switch** (`InputWatchdog`, shared with the native engine): every inbound message refreshes a liveness timestamp, the client heartbeats its full held-input state every 100 ms while anything is held, and silence releases what is still down — 250 ms for ordinary keys (before the ~500 ms typematic delay, so no repeat is ever generated), 3 s for `hold`-flagged inputs (WASD/ZQSD — the same physical codes — plus mouse buttons and gamepads in gaming mode, so a hiccup does not stop a player mid-stride). Each heartbeat is also a resync: anything released mid-stall but genuinely still held comes straight back. Older clients that never send `inputstate` never arm the watchdog.
- Clipboard: bidirectional text via `paste` events + `ClipboardBridge` (host==backend only).

## 5.6 Session lifecycle & teardown discipline

### Stream worker processes & the two slots

`stream_worker_enabled` (default **on**) runs every session in a `MoonlightWeb --stream-worker` **child process** (`StreamWorkerHost` parent-side, `worker/StreamWorkerMain.cpp` child-side; JSON lines over stdin/stdout). Since `moonlight-common-c` is process-global, one process = one session — so child processes are what buy **concurrent slots** (plus crash isolation: a relay crash no longer takes the web server down).

| Slot | Signaling / relay ports | Browser path | Role |
|---|---|---|---|
| 0 | 48001 / 48002 | `/ws`, `/ws/stream` | The live stream. |
| 1 | 48011 / 48012 | `/ws1`, `/ws1/stream` | The **standby** leg of seamless quality switching. |

**Seamless switching** (quality step, HDR/codec change, congestion degradation): the frontend launches the *other* slot with `{standby:true, session_slot}` and its own derived `client_uniqueid`, keeps the live stream playing, and swaps the display only on the standby's **first decoded frame** — the user never sees a loader. A standby launch never takes over slot 0; it joins the already-running Sunshine app (`preferResume`).

Rules specific to the dual path:

- **A standby launch is the capability probe.** Hosts that refuse a second concurrent session are remembered per host (`dual_supported:false` / `status:"dual_unavailable"` in the `/start` response) and the frontend reverts to the plain relaunch (quit, then launch again). Heuristic backstop: slot 0 dying within ~3 s of a standby launch means the host took over instead of adding a session.
- **Always retire, never plain-quit, when a twin stream exists.** The frontend's `quit({retire:true})` sends `keep_host_session:true`, which disconnects the leg *without* a Sunshine `/cancel`. Both legs share one Sunshine app: a `/cancel` kills the surviving leg too and cascades into `Failed to decrypt RTSP` on it. This applies to the standby swap **and** to the plain relaunch path.
- `/quit` with `session_slot` tears down that slot only; without it, every slot owned by the caller's `client_uniqueid`.
- The parent tracks which uniqueids still have a live Sunshine app (workers are fresh processes with no in-process resume hint), so a relaunch goes straight to `/resume` — Sunshine rejects `/launch` while an app is running.
- Set `stream_worker_enabled:false` to fall back to the in-process, single-stream mode; the ordering rules below then apply in-process and are also what the worker executes internally.

### Ordering rules

These prevent whole bug classes (crashes, 504s, zombie sessions):

1. Frontend quits by calling `webrtc.close()` **before** HTTP `/quit` (a `_stopping` guard silences `onerror`; `close()` uses its own `_closed` guard).
2. Backend `/quit` and all teardown paths stop the **shim first** (`stopConnection()` — moonlight stops calling back), then `relay->stop()`, then `deleteLater()`.
3. `/quit` is ownership-guarded by `client_uniqueid` — a stale quit from a taken-over client cannot kill the new owner's stream.
4. Relay teardown lambdas live in `qApp` context in `main.cpp` (the ephemeral `StreamSession` self-deletes once streaming starts, so it cannot own teardown).
5. A new `/start` **defers** until the previous relay graph emits `destroyed()` (frees the fixed signaling port + the moonlight singleton).
6. Take-over never `/cancel`s Sunshine — the newcomer `/resume`s the same session.
7. Revoking a streaming auth session triggers the same teardown plus a keyed Sunshine quit.
